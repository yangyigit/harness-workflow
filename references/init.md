# 初始化与 AGENTS.md 拆分

依据：入口文件是路由器，不是百科。`AGENTS.md` 控制在 50-200 行，只放每次任务都要用的内容。专题文档每篇 50-150 行，按需读取。全局硬约束不超过 15 条，重要的放在顶部或底部，别埋在中间。
来源：https://walkinglabs.github.io/learn-harness-engineering/zh/lectures/lecture-04-why-one-giant-instruction-file-fails/

## 1. 判断新老项目

满足任意一条就算**老项目**：
- 已有 `AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`.cursor/rules/`、`.github/copilot-instructions.md` 之一
- 业务源码文件超过约 20 个（不算依赖、构建产物和锁文件）
- git 提交超过约 10 次

都不满足就是**新项目**。判断结果用一句话告诉我，我可以纠正。

| | 新项目 | 老项目 |
|---|---|---|
| 是否拆分 | 直接拆，不问 | 先问，见第 3 节 |
| 信息来源 | 现有代码 + 问我 | 读代码为主，问我为辅 |
| 已有规则文件 | — | 合并进来，不删除 |

## 2. 读代码（只读，不改）

按下面的顺序收集事实，每条都记下来源路径。用 `rg --files`、`git log --oneline | head`、直接读配置文件就够了，不写扫描脚本。

1. 清单文件：`package.json`、`pnpm-workspace.yaml`、`pyproject.toml`、`go.mod`、`pom.xml`、`Cargo.toml` 等。从中拿到语言、框架和版本、关键依赖、脚本命令
2. 目录结构：看顶层两层目录，得出模块划分；monorepo 要列出每个包
3. 入口：`main.*`、`index.*`、`App.*`、路由文件、服务启动文件
4. 配置：构建（vite、webpack、tsconfig）、lint 和格式化（eslint、prettier、ruff）、测试（vitest、jest、pytest）、CI（`.github/workflows` 等）、环境文件。环境文件只记文件名，不读密钥
5. 抽样代码：每类最多 1 个，总共不超过 8 个。比如一个页面或接口、一个 store 或 service、一个组件或模型、一个测试、一个工具函数。目的是提炼项目里真实的命名和写法
6. 已有规则：README、`CONTRIBUTING`、第 1 节列出的 agent 规则文件、`GLOSSARY.md`、`docs/adr/`

读完以后，只问**代码里读不出来的**，一次最多 5 个。比如：
- 用一句话说，项目是做什么的、给谁用
- 验证命令是不是 `xxx`（列出我推断的）
- 有没有绝对不能碰的目录或做法
- 代码里两种写法并存时，以哪种为准

不知道的标「待确认」，不要编。

## 3. 老项目：先问拆不拆

读完代码后，先给出预估再问：

> 这是老项目（已有 CLAUDE.md，约 180 个源文件）。按读到的内容，写成单个 AGENTS.md 大约 260 行。怎么处理？
> 1. 拆分：入口 AGENTS.md + docs/agents/ 专题文档（推荐）
> 2. 不拆：单个 AGENTS.md，压到 200 行内，细节只留链接
> 3. 只补缺：保留现有 AGENTS.md，只追加缺的章节

- 已有 `AGENTS.md` 的，动手前先给我看差异摘要
- 已有 `CLAUDE.md` 等文件的，把内容合并进来，原文件保留。可以建议把 `CLAUDE.md` 改成一行 `@AGENTS.md` 引用，但由我决定
- 预估不超过 120 行的老项目，也照样问，但推荐项改成「不拆」

## 4. 拆分结构

```
AGENTS.md                     入口，≤200 行，目标 120 行内
docs/agents/
├── project.md                项目介绍：做什么、给谁用、核心流程
├── architecture.md           架构与模块：职责、依赖方向、数据流、边界
├── stack.md                  技术栈：框架、版本、关键依赖、用法要点
├── conventions.md            规范：命名、目录、写法、错误处理、测试、提交
├── commands.md               命令：安装、开发、构建、测试、lint、发布
└── progress.md               当前任务、基线、待办、交接
<模块目录>/AGENTS.md           可选：大模块自己的规则，50-150 行
```

- 术语写进 `GLOSSARY.md`，决策写进 `docs/adr/`，都由 Matt 的 `domain-modeling` 维护。init 时不主动建这两处；读到已有的，在 `project.md` 里链接过去
- `docs/agents/` 下的 `issue-tracker.md`、`domain.md`、`triage-labels.md` 是 Matt 的配置文件名，不要占用
- 某篇专题不到 20 行，就并进入口或相邻的专题，不要硬拆
- 某篇超过 150 行，按子主题再拆，比如 `conventions-api.md`、`conventions-ui.md`
- 某个模块有独有规则且超过 30 行，下沉为该目录下的 `AGENTS.md`（Codex 等工具会就近读取）
- 拿不准放哪时：每次任务都用的，放入口；某类任务才用的，放专题；某个目录才用的，放模块 AGENTS.md；基本用不上的，不写

新项目代码还很少时，专题里大部分章节会是空的。那就只建入口和 `conventions.md`、`commands.md`、`progress.md`，其余等代码长出来再拆。入口的文档索引只列已存在的文件。

## 5. 入口 AGENTS.md 写什么

顺序固定，模板见 `assets/templates/AGENTS.md`：

1. **项目概览**：两三句话，说清是什么、技术栈、仓库形态
2. **快速命令**：安装、开发、测试、完成前必跑，各一行
3. **硬约束**：不超过 15 条，每条一句话并写明违反后果。只放真会出事的
4. **模块地图**：每个模块一行，写路径和一句话职责
5. **文档索引**：每篇专题一行，写路径、内容、**何时必读**
6. **工作方式**：一行，指向本 skill
7. **底部重申**：把最关键的 2-3 条硬约束再写一遍，防止埋在中间被忽略

`setup-matt-pocock-skills` 之后会在入口追加一个 `## Agent skills` 小节（约 10 行），行数预算要留出这部分。

不放进入口：超过 10 行的代码块、工具手册、历史事故经过、只有某个模块才用的规则。

## 6. 专题文档写什么

每篇开头用一行写明「何时读」。内容要求：
- 结论带证据路径，比如：状态管理用 Pinia setup store（`src/stores/user.ts`）
- 规范要写成可检查的句子，比如：接口函数统一放在 `src/api/<模块>.ts`，返回 `Promise<Result<T>>`。不要写「保持代码整洁」这种话
- 规则分三级：**必须**（违反会出错）、**优先**（默认这么做）、**参考**（了解即可）
- 推断出来但还没确认的，标「待确认」

各篇的重点：
- `project.md`：业务目标、用户角色、3-5 条核心流程，术语和决策链接到 `GLOSSARY.md`、`docs/adr/`
- `architecture.md`：模块表（路径、职责、依赖谁、被谁依赖），分层和依赖方向，1-2 条关键数据流，不能跨越的边界
- `stack.md`：框架与版本表，每个关键依赖的用途和在本项目中的用法约定，不要引入的替代库
- `conventions.md`：命名、目录、组件或函数写法、错误处理、日志、测试的位置和命名、提交信息格式
- `commands.md`：每条命令的作用、前置条件、大致耗时，以及哪条是「完成前必跑」

## 7. 完成检查

写完后自查，并把结果报告给我：
- [ ] 用 `wc -l AGENTS.md docs/agents/*.md` 确认入口不超过 200 行、专题不超过 150 行
- [ ] 硬约束不超过 15 条，最关键的既在顶部，也在底部重申
- [ ] 入口里每篇专题都写了「何时必读」
- [ ] 验证命令真跑过一次，结果写进 `progress.md` 的「基线」。如果是红的，说明是基线问题
- [ ] 所有「待确认」都列出来：逐条问我，或一次列完让我挑

最后给我一份摘要：生成了哪些文件、各多少行、还有哪些待确认。然后提示 `setup-matt-pocock-skills`。
